## Code Canonicality

Same logic has exactly one implementation in the repo. Version evolution belongs in git history, not filenames.

- Before adding any function, class, module, or file: grep for existing similar implementations. If found, extend or refactor the existing one. Only create new if truly absent.
- Forbidden suffixes for filenames, class names, function names, module names: `_v1`, `_v2`, `_new`, `_old`, `_backup`, `_temp`, `_copy`, `_final`, `_real`, `_improved`, `_refactored`, `_fixed`, `_legacy`, `_deprecated`. Existing ones are debt to unify, not patterns to extend.
- Refactor in place: commit the working state first, modify the original file, run tests. If it breaks, `git revert`. Never keep an old version alongside the new "just in case" — git is the safety net.
- No parallel implementations as a transition. Replace atomically.
- Commented-out code is a lint error, not a safety net. Delete it; git remembers.
- Unreferenced exports and dead code paths are debt. Wire them up in the same change or delete them.
- Do not use the repo as a scratchpad. `tmp/`, `scratch/`, `backup/`, `_old/`, `deprecated/`, `archive/`, `wip/` must not appear in commits.

## Project Identity

Local, git-native forge: issues, pull requests, review, and merge inside an ordinary git repository — git protocol only, zero resident processes, no GitHub synchronization. Commands surface as `git forge ...` plus thin `git issue`/`git pr` wrappers. L1 is single-user, single-machine, single repository.

- **Primary consumers**: the developer (CLI), and the devflow multi-agent pipeline that implements the L1 feature plan.
- **Lifecycle**: months-scale MVP (L1 milestone, L2 features deferred).
- **Team scale**: single developer + AI agents.
- **Strictness profile**: L3 (strict) — chosen explicitly at init; thresholds live in `constraints.yaml`. Re-run `eng-init` to change the profile; do not relax individual gates ad hoc.
- **AI tools targeting this repo**: devflow (`implement` skill) as mission orchestrator; `eng-init` maintains this harness.
- **Domain language**: `CONTEXT.md` is the canonical glossary (Issue, PR, Forge Event, Event Chain, Review, Forge Ref, Counter Ref, Merge Gate). Check it before naming domain concepts.


> the script preflights this and exits 1 with a clear one-line error when any requirement

## Conventions

- **TDD required** (L3): every production change ships with a failing test first; no merge without the red→green cycle.
- **Rust**: `Result<T, E>` everywhere; no `unwrap()`/`expect()` outside tests and `main`; `pub(crate)` by default; no `pub` item without doc comments; no `println!`/`eprintln!` outside `main`; borrow over clone.
- **Commits**: conventional types (`feat/fix/refactor/chore/docs/test/ci/build/perf`); one logical change per commit.
- **Coverage**: 80% line minimum (global); per-file 100% strong form not elected. An uncovered line in a hot path is a dead-code candidate, not a missing test to bolt on.
- **Docs change with code**: if a change alters behavior described in `docs/architecture/git-forge.md`, `CONTEXT.md`, or AGENTS.md, update them in the same change.
- **Decision records**: non-trivial changes ship their record in `docs/decisions/<zone>/<kind>/` in the same change (note-required rule); see `docs/decisions/README.md`.

## Code Review Self-Check

Before submitting or accepting a review, verify:

- Tests were red before the fix (or genuinely new coverage), then green.
- Wire contract conformance: ref layout, event schema v1, CAS semantics per architecture doc.
- No `unwrap()`/`expect()` in production paths; no panic paths reachable from CLI input.
- No dead code, no commented-out code, no scratchpad artifacts.
- Docs updated in the same change where behavior changed.
- Enforcement index rows: does the change touch a block-level gate and pass it?

## Critical Paths

White-box review required for changes touching these (L3): `src/store.rs` (git2 ref transactions, counter CAS, immutable snapshot refs) and merge gate/merge execution (`src/cli.rs` merge-gate predicate, merge strategies in `src/git.rs`, temporary worktree handling, pending-result ref). These are irreversible operations — ref writes and merges mutate the repository. Any diff touching a critical path is flagged for human review.

## Agent Operating Rules

- **Read this file, `CONTEXT.md`, and `docs/architecture/git-forge.md` before working.**
- Devflow mission state is scheduler-owned: never edit `.specs/*/missions/` files (`state.json`, `features.json`, `progress_log.jsonl`, `validation-state.json`, handoffs) directly. State changes go only through `devflow.cjs` subcommands (`end-feature`, `record-verdicts`, `reconcile`, …).
- Never submit a receipt that is not backed by real work: a success receipt requires a real commit with a non-empty diff; a validation receipt requires per-assertion evidence. Faking a receipt is a trust violation.
- Before reporting failure, revert your own edits — the scheduler refuses to spawn into a dirty worktree.
- Evidence: verification claims require fresh evidence from the current session (command + exit code + output). No "I ran it before" claims.
- Out-of-bounds: do not modify `docs/adr/` (frozen history); do not edit archived decision records; do not modify user-owned `.gitignore` content without reason; do not run `git clean -fdx` inside a mission (deletes the devflow runtime).
- Commit discipline: commit only when the user requests it or the workflow requires it (devflow workers commit per feature). Stage only intended paths.
- Escalation: a validator reporting a blocker no worker can clear (missing credentials, external service) escalates to the user — do not requeue the same unverifiable step.
